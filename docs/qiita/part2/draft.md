# Audio Spectrogram Transformer で日本のカモ8種の鳴き声分類器に挑戦　Part2🦆

## はじめに

[Part1](https://qiita.com/mushipi/items/dddf9780b95d75c63e9d) では、Xeno-canto から集めた日本のカモ8種の鳴き声を Audio Spectrogram Transformer（AST）で fine-tuning し、`test f1_macro ≒ 0.838`（run05）までたどり着きました。

そして Part1 は、こんな宿題を残して終わっていました。

- ハイパーパラメータをいくら調整しても `0.84` の天井が破れない
- 本質的なボトルネックはモデルではなく **データの側**（録音数・チャンク数の不均衡）にありそう
- 「録音数の少ない種の音源を増やす」「SpecAugment をクリーンに評価する」「モデル選択の仕組みを見直す」

Part2 はその続きです。結論から言うと、**この宿題のほとんどは「予想と違う形」で決着しました**。

- 「データを増やせば天井が破れる」→ **増やしたら悪化した**
- 「チャンク数の不均衡が真犯人だ」→ **不均衡を直しても何も変わらず、仮説が崩壊した**
- そして最終的に、**そもそも解くべき問題を間違えていた**ことに気づきます。

run06 から run11 までの試行錯誤と、終盤の「パラダイム転換」を、失敗も含めて正直に書いていきます。例によって長いです。お茶でも淹れてきてください🍵

> 対象8種：マガモ / コガモ / オナガガモ / ハシビロガモ / ヒドリガモ / キンクロハジロ / ホシハジロ / ホオジロガモ

## 第1章：天井を破ろうとして、ことごとく失敗する（run06〜run09）

Part1 の最後で、種別の性能を分析した結果「**録音数20本のキンクロハジロ（Tufted Duck）とヒドリガモ（Eurasian Wigeon）が極端に弱い**」ことが分かっていました。特にキンクロハジロは奇妙な振る舞いをしていて、

- train のチャンク数は **694と最多**なのに
- test の F1 は最低クラス
- しかも **precision 0.269**（=Tufted と予測したものの 7割が外れ）と、他種を大量に吸い込む「過剰予測」状態

「チャンクは多いのに弱い。これはチャンクの"数"ではなく、録音が20本しかない="多様性"の問題ではないか」というのが Part1 で得た仮説でした。

この章は、その仮説を潰しにいく4連戦の記録です。先に結果の全体像を出しておきます。これから出てくる run は、ほぼ全部この1枚に乗っています。

![run05からrun11までのtest f1の推移](qiita_figures/fig1_run_trajectory.png)

**図1**｜run05→run11 の test f1 推移。青＝10秒チャンク時代、橙＝3秒チャンク時代、点線＝Part1到達点(0.838)、赤帯＝1 run分の95%信頼区間。
👁 **読み方**：点が上下しているより、**ほぼ全部が赤帯の中に収まっている**ことに注目。run間の差はノイズの範囲です。

何をやっても 0.838 を超えられず、むしろ右肩下がり。この「下がり続けるグラフ」が Part2 の主役です。

> ⚠️ **先に統計的な白状をしておきます。** このグラフの run 間の差（0.011〜0.028）を「改善した／悪化した」と語るのは、実は危うい。test の母数は録音数で言うと**わずか73本**しかなく、しかもチャンクは同じ録音から切り出されていて独立ではありません。run10 の予測で **録音単位のブートストラップ**（録音を塊ごと再標本化）を回すと、macro-F1 の 95% 信頼区間は **[0.679, 0.843]、幅 0.164** にもなります（赤帯）。
> つまり **run06〜09 の上下動は、ほぼ全部このノイズ帯の中**。本記事では「断定」ではなく「**傾向と、機構が確認できた介入だけ**」を信じる、というスタンスで読んでください。後述の run09（特定録音の削除で誤判定が 13→4 に減る）のような**大きく機構的な変化**は信用できますが、`−0.011` 単位の差で一喜一憂してはいけない、というのが正直なところです。

### run06：SpecAugment 単独投入 → 失敗（test f1 0.810）

まず宿題のひとつ、SpecAugment をクリーンに評価しました。Part1 の run02 では複数パラメータと同時に変えてしまって切り分け不能だったので、今度は **SpecAugment だけ** を入れます（1 run 1 変更の原則）。

仮説はこうでした。

- **H1a**：SpecAugment で train_loss は上振れするはず（暗記が妨害されるから）
- **H1b/H2**：その結果 overfit が抑えられて test f1 が上がるはず

結果：

| | run05（base） | run06 |
|---|---|---|
| val f1_macro | 0.840 | **0.846**（epoch 2）|
| test f1_macro | **0.838** | 0.810（−0.028）|

H1a は成立（train_loss は実際に桁単位で上振れした）。でも H1b/H2 は不成立。**val は上がったのに test は下がる**という、Part1 で痛い目を見たパターンの再来です。

種別に見ると、狙っていたキンクロハジロは +0.05 改善したのに、ハシビロガモが **−0.19** と大崩れして全体を押し下げていました。

**学び**：「train の暗記を抑制する」ことは「汎化する」ことを保証しない。SpecAugment のような正則化系の手法は val 曲線の"形"を変えてしまい、`load_best_model_at_end`（val 最良エポックを採用する仕組み）との相性が悪いと、むしろ早すぎるエポックを掴んで test 性能を落とす。

### run07：弱い2種に録音を +10 ずつ追加 → 失敗（test f1 0.827）

次は本丸、「録音数が少ない種にデータを足す」です。キンクロハジロとヒドリガモに、quality=B の録音を +10本ずつ追加しました。

このとき地味に大事だったのが、**test セットを固定したまま** train だけ増やすこと。新規録音が test に漏れたら比較になりません。`preserve-existing` 方式で既存の split を保持し、追加分だけ train に入れました。

結果：

| | run05 | run07 |
|---|---|---|
| test f1_macro | **0.838** | 0.827（−0.011）|

また下がりました。しかもキンクロハジロの precision は 0.269 → 0.296 とほぼ動かず、過剰予測は解決していません。さらに、いじっていないはずのマガモ（−0.029）やハシビロガモ（−0.108）まで悪化する **負の波及**が起きました。

ここで犯人の輪郭が見えてきます。録音を10本足すと、その録音から **チャンクも増える**（Tufted の train チャンクは 694→728）。つまり「録音の多様性を上げたい」という意図とは裏腹に、「チャンク数の不均衡」をさらに悪化させていたのです。

**学び**：録音追加とチャンク上限（cap）は**同時にやらないと意味がない**。多様性を足すつもりが、不均衡を足していた。

### run08：チャンク数を半減 → 仮説が完全に崩壊する（test f1 0.820）

ならばと、今度は逆方向。録音はそのままに、キンクロハジロのチャンクに **cap=100** をかけて train チャンクを 728→361 へ半減させました。他種はいじりません。これで「チャンク不均衡こそが過剰予測の原因」という仮説をきれいに検証できるはずでした。

予測：チャンクを半分にすれば、過剰予測（precision 0.269）が緩和されるはず。

結果：

| | run05 | run08 |
|---|---|---|
| キンクロハジロ precision | 0.269 | **0.269** |

…**小数第3位まで完全に同じ**でした。

![run08でチャンクを半減してもprecisionが変わらない](qiita_figures/fig2_run08_collapse.png)

**図2**｜左＝介入（キンクロのtrainチャンクを728→361に半減）、右＝結果（precision）。
👁 **読み方**：左であれだけ減らしたのに、**右の棒の高さが2本とも0.269で完全に同じ**。狙った原因（チャンク数）をいじっても結果が動かない＝仮説が外れた、という1枚です。

チャンクを半分にしても、誤って吸い込む構成（コガモ13件・ヒドリガモ4件…）まで run05 とほぼ同一。これには本当に驚きました。**「チャンク数の不均衡が過剰予測を生む」という仮説が、ここで完全に崩壊しました。**

ついでに、いじっていないマガモ（−0.069）・ヒドリガモ（−0.049）が大きく悪化。局所的な介入のはずが、学習ダイナミクス全体に波及していました。

**学び**：真のボトルネックはチャンクの"数"ではない。音響的な類似性か、特定のデータの中身か、モデルの容量か。**チャンク数をいじるアプローチでは永遠に解決しない**ことが、反証によってはっきりした。

### 探偵パート：誤分類を1件ずつ音で聴く

run08 で手詰まりになったので、戦略を変えました。集計をやめて、**誤分類された音声を1件ずつ実際に聴く**ことにしたのです。

すると、衝撃的なほどきれいなパターンが見えました。

- キンクロハジロと誤判定された**コガモ13件のうち12件**が、同じ録音 **XC197026（幼鳥の鳴き声 / juvenile call）** から出ていた
- 誤判定された**ヒドリガモ4件は、全て** **XC349677（オスメスの掛け合い）** から出ていた

誤分類はランダムにばらけているのではなく、**特定の録音に異常に集中**していたのです。

![誤判定がXC197026とXC349677に集中し、削除で消える](qiita_figures/fig3_recording_concentration.png)

**図3**｜「キンクロと誤判定された件数」を録音別に、長尺2録音の削除 前（赤）／後（緑）で比較。
👁 **読み方**：誤りが2つの録音にだけ集中していて、その録音をtrainから消すと**13→4・5→0 と激減**。「特定の録音が決定境界を歪めていた」証拠です。

さらに調べると、train データのコガモには `stage=juvenile`（幼鳥）の録音が **1件しかありません**でした。test には幼鳥がいるのに train にはほぼいない——典型的な **distribution shift（分布のずれ）** です。

ここで仮説が更新されます。

> 真犯人は「チャンクの数」ではなく、**キンクロハジロの長尺2録音 XC488112（45分）/ XC488113（49分）が決定境界そのものを歪めている**のではないか。

### run09：長尺2録音を完全削除 → 仮説は確証、でも代償が大きすぎた

仮説を確かめるため、問題の2録音 XC488112 / XC488113 を train から **完全に削除**しました（Tufted チャンク 361→161）。

結果は、仮説の核心を見事に確証しました。

- XC197026 がキンクロハジロと誤判定される件数：**13 → 4**
- XC349677 がキンクロハジロと誤判定される件数：**5 → 0**

run08（チャンク半減）では1ミリも動かなかった現象が、**特定録音の完全削除では動いた**。原因は「チャンクの数」ではなく「**特定の録音が教え込む音響パターンの幅**」だったのです。

ただし、代償が大きすぎました。キンクロハジロの train データが減りすぎて recall が 0.700 → 0.300 へ崩壊。test f1 も 0.810（run05 比 −0.028）まで落ちました。

**学び**：原因は特定できた。でも「過剰予測の解消」と「適正な学習量の確保」を両立させる中間点が必要。真のレバーは「データ・ハイパラ・モデル」のどれでもなく、**特定録音のキュレーション**だった。

ここまでで分かったことを一行でまとめると：

> **このタスクの精度は、ハイパラではなく「どの録音を train に入れるか」で決まっていた。**

## 第2章：そもそも前提が間違っていた（run10 / 3秒チャンクへの転換）

run09 で「中間 cap を探ろう」としていたところで、もっと根本的な設計ミスに気づきます。

開発環境を Windows から Ubuntu に移したついでに、後段で連携する予定の **BirdNET-Analyzer のソースコード**を読んだのです。すると：

```python
# birdnet_analyzer/model.py
keras.Input(shape=(144000,))   # 48kHz × 3秒 = 144000 サンプル
```

```python
# birdnet_analyzer/audio.py
def split_signal(..., seconds=3.0):  # デフォルト3秒窓
```

**BirdNET は 3秒窓で音声を処理していました。**

このプロジェクトの設計思想は「BirdNET が"カモ類"と検出した音声を受け取って、8種に細分類する」というものです。つまり後段の AST には **3秒のチャンク** が渡ってくるはず。なのに、**学習はずっと10秒チャンクでやっていた**のです。

これは推論時に7秒分のゼロパディングが発生する、明確な設計不整合でした。run09 の cap 実験より、こちらを先に直すべきです。10秒 → 3秒へチャンク長を変更し、run10 としました。

### 位置埋め込みのリサイズ

AST は入力長に対応した **位置埋め込み（position embedding）** を持っています。10秒前提の事前学習済みモデル（1214次元）に3秒の入力（350次元相当）を食わせると次元が合いません。

そこで、事前学習済みの位置埋め込みを **線形補間で 1214 → 350 次元にリサイズ**してから学習する方式を実装しました（`resize_position_embeddings()`）。

> ⚠️ ハマりどころ：リサイズ後に `model.config.max_length` を更新し忘れて、保存された config.json（max_length=1024）と実際の重み（350次元）が食い違い、評価時にロードエラー。地味に時間を溶かしました。

### run10 の結果：狙いは当たったが、全体は下がった

| | run05（10s） | run10（3s）|
|---|---|---|
| test f1_macro | **0.838** | 0.782（−0.056）|
| **キンクロハジロ F1** | 0.389 | **0.738（+0.349）** |

ずっと苦しめられてきた**キンクロハジロが、ようやく改善しました**。長尺2録音を除外しつつ、3秒チャンクで train 477チャンクを確保でき、「過剰予測の解消」と「適正な学習量」が初めて両立したのです。第1章の探偵編が、ここで報われました。

![run05とrun10の種別F1比較。キンクロハジロが大幅改善](qiita_figures/fig4_per_species.png)

**図4**｜種ごとの test F1。青＝run05（10秒）、橙＝run10（3秒）、緑＝注目のキンクロハジロ。
👁 **読み方**：**キンクロだけ 0.39→0.74 と跳ね上がり**、他種は橙が少し低い（トレードオフ）。※両runで test の母数が違うので「傾向」として見てください。

一方、全体の f1 は下がりました。考えられる理由は主に2つ。

1. **位置埋め込みの適応コスト**：事前学習の文脈（10秒）から離れた分、汎化が落ちた
2. **3秒チャンクは1チャンクあたりの情報量が少ない**：10秒の約1/3。オナガガモ・ハシビロガモのようにもともとチャンクが少ない種は、実質的な学習情報量がさらに減った

> ⚠️ ただし**フェアに言うと、これは「3秒が劣る」という結論ではありません**。run10/11 の 3秒モデルは lr も patience も10秒時代のまま、**チューニングを一切やっていない**。位置埋め込みを補間した直後の、まだ適応しきっていないモデルです。「**未チューニングの3秒では下がった**」が正確な表現で、3秒体制を詰め直す run（lr↓・patience拡大）は今後の宿題として残っています。0.838 と 0.782 を実力差として並べるのは早計です。

それを踏まえても、run10 は「**スコアの絶対値より、後段パイプラインと整合する正しい土台に乗り換えた**」run だと考えています。ゼロパディングだらけの 10秒モデルより、3秒で素直に動くモデルの方が本番では正しい——という判断です。

## 第3章：解くべき問題を間違えていた（run11 / Outlier Exposure）

ここで、もっと大きな問題に向き合うことになります。

これまでずっと、8種分類器の **f1 を上げること** に必死でした。でも、よく考えてください。

> 本番では、BirdNET が「カモ類」と判定した音が AST に流れてきます。でも BirdNET は誤検出します。学習に使っていない**カルガモ・オカヨシガモ**のような他のカモが流れてくることもあるし、そもそもカモですらない音が混ざることもある。

**そのとき、softmax は必ず8種のどれかに分類してしまう。**

カルガモの声を聞かせても、自信満々で「マガモです」と答える。これは f1 をいくら磨いても解決しません。**閉世界仮定（学習した8種しかこの世にいないという前提）で、開世界の問題を解こうとしていた**のです。

これは「分類精度」の問題ではなく「**未知を未知と言えるか（OOD検知 / Out-of-Distribution Detection）**」の問題でした。

### まず素朴な2手法を試す（run10モデルで評価）

未知を弾くための「自信度スコア」を、まずは2つ試しました。

**手法①：Softmax Confidence**
`max(softmax(logits))` が低ければ未知とみなす、という素朴な方法。

- AUROC = 0.838、FPR≤5% の推奨閾値 = 1.00（**実質使用不可**）

失敗の理由は構造的でした。softmax は logit を正規化するので、**全部の logit が小さくても max 値は高く出る**（softmax overconfidence）。「自信がない」ことを softmax は表現できないのです。

**手法②：Energy スコア**

```python
energy = T * logsumexp(logits / T)   # T=1.0、高い=既知 / 低い=未知
```

logit の**絶対スケールを保持する**ため、未知入力で logit が全体的に小さければ自然にスコアが下がります。

- AUROC = 0.894（softmax より +0.056）

改善はしたものの、既知と未知の分布が重なっていて、FPR<5% を保てる実用閾値がまだ存在しませんでした。

### 手法③：Outlier Exposure（run11）→ 採用

そこで、**未知のカモ（カルガモ等7種）を "other" クラスとして学習に混ぜる**ことにしました。これは Hendrycks et al. (2019) の **Outlier Exposure** という手法です。

ここで重要なのは目的の置き方です。**"other" を正確に分類することが目的ではありません。** 目的は「未知データに晒すことで energy 空間を再較正（calibrate）し、既知/未知の分布を引き剥がすこと」です。

設計には、踏みやすい罠がいくつもありました。

**罠①：Double Dipping（二重補正）**
当初「WeightedRandomSampler でクラスを均等化 ＋ Loss にデータ数ベースの重みを掛ける」と考えました。でもこれは二重補正です。Sampler でバッチ内比率を既に均等にしているのに、さらにデータ数ベースの重みを掛けると、"other" の勾配が爆発して8種の決定境界を破壊します。

→ 採用：Sampler で均等化し、Loss 重みは「Recall を上げたい意図」の **固定値 α=1.5** のみ（データ数ベースは捨てる）。

**罠②：SpecAugment をどこに掛けるか**
run06 で「8種に SpecAugment を掛けると境界が壊れる」と実証済み。一方で "other" は過学習防止のために波形多様性が欲しい。

→ 採用：`if label == other_label_id` の条件分岐で、**"other" クラスにのみ** SpecAugment を適用。理論と実利が完璧に一致する解でした。

**罠③：モデル選択基準**
9クラス全体の f1 を選択基準にすると「other は高いが8種が壊れたモデル」が選ばれかねない。

→ 採用：`metric_for_best_model = f1_macro_8class`（8種だけの F1）。other の recall はログには出すが、モデル選択には使わない。

### run11 の結果

| 指標 | run10 | run11 | 差分 |
|---|---|---|---|
| **AUROC (energy)** | 0.894 | **0.932** | +0.038 |
| test f1_macro（8種）| 0.782 | **0.793** | +0.011 |
| val other_recall | - | 0.090 | ※目的外 |

`other_recall = 0.090` という低い値を見て「失敗では？」と一瞬思いました。でもこれは Outlier Exposure としては **正しい挙動**です。energy 空間で既知/未知が分離された結果として、softmax 空間ではきれいな境界が引けない——という構造的な帰結であり、`AUROC 0.932` こそが目的達成の証拠なのです。

energy スコアの分布を見ると、既知（In-dist）と未知（OOD の3 Tier）がはっきり別の山に分かれているのが分かります。「分類精度」ではなく「分布の分離」を狙った設計が効いています。

![energyスコアの分布。In-distとOODが分離](qiita_figures/fig5_energy_violin.png)

**図5**｜energyスコアの分布。左＝既知の8種（In-dist）、右3つ＝未知（OODの3カテゴリ）。
👁 **読み方**：**左の山（既知）だけが上に位置し、右の3つ（未知）と分かれている**。この上下の隙間に閾値を引けば未知を弾けます。

ROC で見ても、素朴な softmax（AUROC 0.838）からここまで改善しました。赤い点が FPR≤5% を満たす運用閾値（10.35）です。

![energyスコアのROC曲線 AUROC0.932](qiita_figures/fig6_roc_energy.png)

**図6**｜energyゲートのROC曲線（AUROC=0.932）。赤い点＝採用した運用閾値10.35（誤受容率FPR≤5%）。
👁 **読み方**：曲線が**左上に張り付くほど性能が良い**。AUROCは1.0が満点で、0.932はかなり上手に未知を弾けていることを示します。

これに気づいたとき、「分類器で何とかしよう」という発想自体が間違いで、**未知の棄却はモデルと独立した"ゲート"でやるべき**だと腑に落ちました。

> ⚠️ **この 0.932 を過信してはいけません。** in-dist も OOD も、両方 Xeno-canto の quality=A 録音です。種が違えば録音者・マイク・場所も違うので、energy が分けているのは「種の音響特徴」ではなく「**録音環境の違い（SNR・帯域・無音率）**」かもしれません（ショートカット学習の懸念）。さらに本番で BirdNET が誤検出して流れてくるのは、こんな綺麗なカモ録音ではなく**風・波・無音・他の鳥**です。つまり 0.932 は「**整えられた OOD での値**」であって、実フィールドの failure distribution に対する保証ではありません。閾値 10.35 も Xeno-canto 較正なので、現場では引き直しが前提です（後述）。

### 完成したパイプライン

```
入力音声（3秒チャンク）
    ↓
AST run11 → logits（9次元：8種 + other）
    ↓
energy = logsumexp(logits)
    ├─ energy < 10.35 → "unknown"（未知として棄却）
    └─ energy ≥ 10.35 → argmax(logits[:8]) → 8種の予測
```

閾値 `10.35` は FPR≤5% を満たす点として算出。これらは全て `species_taxonomy.yaml` で管理し、モデルの重みを一切変えずに FPR/TPR のトレードオフを調整できる設計にしました。

```yaml
pipeline:
  energy_threshold: 10.35    # FPR≤5% での推奨値
  energy_temperature: 1.0    # 将来 Temperature Scaling を試すとき用
```

## まとめ：Part2 で学んだこと

正直に振り返ります。

**うまくいかなかったこと**
- run06〜09 の試行錯誤では、**0.84 の天井を一度も破れなかった**（とはいえ、その run 間の差は信頼区間の中＝有意とは言えない）
- 「データを増やせば伸びる」「チャンク不均衡が真犯人」という直感は、**どちらも実験で否定された**（特に後者は run08 で機構的に反証）
- 3秒チャンクへの移行で 8種分類のスコアは下がったが（0.838 → 0.793）、これは**未チューニングの3秒での値**であって「3秒が劣る」結論ではない

**うまくいったこと**
- 集計をやめて**誤分類を1件ずつ聴く**ことで、真因（特定録音による決定境界の歪み）にたどり着けた
- run08 の**反証** → 音響分析 → run09 の**確証**、という科学的な切り分けが機能した
- BirdNET のソースを読んで**前提のズレ（10s vs 3s）**を発見し、本番と整合する土台に乗り換えられた
- そして最大の収穫は、**「解くべき問題は f1 ではなく OOD 検知だった」と気づけたこと**。Outlier Exposure + Energy ゲートで `AUROC 0.932` に到達した

一番の教訓は、これです。

> **スコアを上げる前に、「そのスコアは本番で意味があるのか」を疑え。**
> 0.84 の天井に頭をぶつけ続けていた本当の理由は、ハイパラでも録音数でもなく、**閉じた世界でしか評価していなかったこと**だった。
