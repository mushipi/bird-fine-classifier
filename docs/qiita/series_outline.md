# Part3「巨大教師から蒸留すれば天井は破れるのか — そして『リーク』に殴られる」🦆

**一行テーマ**: スコアの上げ方ではなく「そのスコアは本物か」を問い続けた回。蒸留は効くが“条件付き”、そして評価そのものが膨らんでいた。

## はじめに（フック）
- Part2 で「OOD検知こそ本丸」と気づき AUROC 0.932 まで来た。だが分類 f1 は依然 0.83 の天井。
- 今回の宿題: **別系統の巨大基盤モデル Perch2.0 を“教師”に知識蒸留(KD)すれば、ASTの天井を破れるのでは？**
- 結論先出し（予想と違う形で決着）:
  - 「蒸留すれば伸びる」→ ASTでは**有意差すら出ない**
  - 「じゃあ効かないのか」→ 素のCNNで試すと**ハッキリ効く**＝KDは“条件付き”の手法だった
  - そして極めつけ: **テストを増やしたら、運用モデルのスコアが“リーク”で膨らんでいた**ことが発覚し、勝敗が逆転する
- 「お茶を淹れて🍵」定型。

## 第1章：別系統の教師という賭け（Perch2.0 → AST 蒸留）
- なぜ Perch か: AST(AudioSet系) と Perch2.0(鳥特化, 1536次元) は**系統が違う**＝相補的な誤りを期待。
- 相補性ゲート（Phase0）: 同一test231録音で AST 0.747 < 教師Perch 0.830 < アンサンブルα0.4=0.844、不一致27%、オラクル余地+0.147 → **強GO**。
- 手法: 教師proba=Perch複数arm平均(linear/mlp/sklearn)、trainは録音単位 **5-fold OOF**（教師の過信回避）、KL温度蒸留 λ/T。
- ⚠白状: 「Phase0で v15=0.747≪教師」は**regime交絡**だった（旧splitで学習したモデルを現testで測った値）。同条件の新規ベースラインは0.826で教師0.830と**ほぼ互角**。→ 罠を踏んだ正直な記述。
- 図: 相補性ベン（AST正/教師正/両方/両方誤）, α掃引でアンサンブルf1。

## 第2章：蒸留したのに、有意差が出ない（結果①AST）
- 録音単位f1(n=231): **C-base 0.8259 / C-kd 0.8510(+0.025) / teacher 0.8304 / ensemble 0.8514**。
- KDは教師を超えアンサンブル水準＝生徒が教師超え（良い蒸留の兆候）。eval_loss **2.229→1.672** でキャリブレーション改善。
- ⚠だが **KD−base +0.025 の 95%CI[−0.022,+0.079]＝0を含む＝有意でない**。231録音の解像度律速（Part2の壁そのもの）。
- 「方向は明確に正・教師超え・損失改善、なのに統計的には確証できない」というモヤモヤ。
- 図: base/kd/teacher/ensemble の点推定＋CIバー。

## 第3章：効くかどうかは“生徒の弱さ”で決まる（結果②素CNN）
- 確証手段の選択: 天井近いASTでは埋もれる → **伸びしろの大きい素の弱モデル(0.39M param 4-conv CNN)に同じKD**を当てれば、効果が大きく有意化しやすい。
- 録音単位f1(n=231): **base 0.4498 → KD 0.5977、+0.148 の 95%CI[+0.084,+0.211]＝★有意(0を除外)**。chunk val も 0.478→0.590。
- → **「KD-from-Perchは本当に効く」を初めて統計的に確認**。AST の +0.025(非有意) は天井近くで伸びしろが小さかっただけ＝同方向・本物と遡及裏付け。
- ハイパラ・グリッド: CNNを試験台に λ∈{0.5,1,2,4}×T∈{1,2,4} → **全12構成がbase超え（Δ+0.048〜+0.208）**＝KDはハイパラ頑健。甘い所=λ≈1・T≈1〜2。
- 図: 弱CNN base vs KD（+0.148 有意バー）, λ×T ヒートマップ。

## 第4章：天井のASTも、多seed soup なら有意化する
- 「単発で非有意なら、運任せを均せばいい」: seed42/1/2 × base/KD を学習。
- KD>base が **3/3 seedで一貫、差+0.027±0.004**（差のSDが絶対値SDより遥か小＝seed引きに依らない）。
- 重み平均 soup: **KD-soup 0.8714**（個々KD最良0.858も超える＝soup典型勝ち）/ base-soup 0.8133。
- **soup-vs-soup: KD−base=+0.0581, 95%CI[+0.018,+0.108]＝★有意**。単発で非有意だったAST KDを多seed soupで「本物かつ有意」に格上げ。
- 図: 3seed一貫性（base vs KD の点群）, soup の効果。

## 第5章：そして“リーク”に殴られる（test拡大Cv2・どんでん返し）
- 動機: 評価の解像度を上げるため test を 231→**289録音**に拡大（薄種をworldwide B級で補強, 1020→1288録音）して全モデル再評価。
- 表面の結果: **Cprod(運用)0.910 ≈ Cv2BASE 0.908 ≈ Cv2KD 0.894 ＝全ペア差なし** → 一見「現行最強・昇格不要」。
- ⚠探偵パート（重複カウント）: ユーザーの「重複しとこう」で発覚 → **運用モデル Cprod は旧trainで学習しており、その録音が Cv2-test に 130/289=45% 混入**＝Cprodの0.910は**テスト半分が学習漏れの膨張値**。整合性: Cv2-train ∩ Cv2-test = 0（Cv2モデルはクリーン）。
- honest 再評価（リークフリー159録音＝3モデルとも未学習）:
  | model | f1 | 95%CI |
  |---|---|---|
  | Cv2BASEsoup | **0.897** | [0.704,0.951] |
  | Cv2KDsoup | 0.822 | [0.625,0.890] |
  | Cprod(運用) | **0.787** | [0.613,0.843] |
- **Cv2BASEsoup − Cprod = +0.110 [+0.042,+0.172] ★有意**（運用を有意超え）。**KDsoup − BASEsoup = −0.076 [−0.164,−0.015] ★有意＝cleanでは蒸留なしが上**。
- 結論の反転: **運用モデルの実力はΔ≈0.12も過大評価**（0.910→honest0.787）。効いたのは**データ拡大＋クリーンsplit**であって蒸留ではない（天井近いAST最終soupにKDは乗らず、clean では base>KD が有意）。
- 図: リークのVenn（旧train∪val ∩ Cv2-test=45%）, 全体評価 vs honest評価で順位が反転する図。

## まとめ（Part3）
- うまくいかなかった: 「蒸留で天井を破る」は AST 最終soupでは否定（cleanでbase>KD）。表面のtest拡大評価は全差なしに見えた。
- うまくいった: **素CNNでKDの有効性を統計的に確定（+0.148）**。多seed soupで論点を整理。そして**リークを暴いて判定を正した**。
- 最大の教訓（格言ブロック）:
  > **昇格判定は、必ず「そのモデルが見ていない録音」で行え。** 0.910 と 0.787 を分けたのは手法ではなく、テストに学習が漏れていたかどうかだった。
- KDの“真価”の再定義: 精度ではなく **(a)弱い生徒で大きく効く (b)seed分散を縮める (c)推論時に教師(Perch,重い)が不要＝CPU運用機にデプロイ可能化**。この(c)が次回の伏線。
- 昇格: 蒸留なし **ast-duck-D-base-soup**（honest 0.897）を運用へ。
- 次Part予告: 「分類器が1個できた。でも**実運用は1種類の分類器では回らない**。BirdNET→群専用Stage2の2段化と、“音では絶対に割れない壁”の話へ」。

# Part4「1種類では足りない — 2段パイプラインと『音で割れない壁』」🦆🦅

**一行テーマ**: 単体モデルを“運用システム”にする。BirdNETの後段に群専用分類器を挿し、最頻種を捨てない誠実な出力を設計する。

## はじめに（フック）
- Part3 で「未知を弾きつつ細分類するコア」は完成。だが現場は **BirdNET が常時走る既存運用**。そこにどう接ぐ？
- 予告転換: Part2 で予告した Jetson/TensorRT は**やめた**。理由＝蒸留で**CPUで足りる**ことが分かったから（Part3の伏線回収）。
- 結論先出し: 2段化は素直に効く。ただし **一部の種は“音では絶対に割れない”** ＝それを精度で殴るのは誤り、設計（複合クラス）で受ける。

## 第1章：2段パイプラインの設計（BirdNET → Dispatcher → Stage2 → Gate）
- 図（全体像）: フィールド録音→Stage1 BirdNET(汎用6千種)→Dispatcher(species_master の group参照)→群別 Stage2(AST)→Energy Gate→DB。
- 群汎用が肝: Dispatcher/Stage2/DBは群非依存、`species_taxonomy.yaml` に群を1行登録するだけで配線（後のParet5で効く）。
- DB非破壊: Stage1列(species/confidence)は不変、Stage2は refined_* 列を追加。原本WAV保持（再実行・監査・ロールバック）。
- ハマりどころ: subprocess隔離（birdnetlib/TF と torch を別venvで分離＝依存衝突ゼロ）、venv_python に .resolve() で symlink が解けて venv 無効化する罠。

## 第2章：蒸留が効く“本当の理由”はデプロイ可能性（CPU運用）
- Part3 で「KDは精度では条件付き」と結論。だが **推論時に Perch(重い・GPU推奨) が要らない**＝蒸留済みAST単体でCPU推論可。
- GT105(CPU)実測: ロード0.8s/RSS452MB→ピーク1.4GB、**推論109ms/chunk(16thread)**、前処理(FE)611ms/chunkが律速。10分バッチ運用に桁違いの余裕。
- → 「Jetson買わなくてよくなった」。蒸留の価値＝精度向上だけでなく**運用機に載せられること**。
- 図: CPU推論レイテンシ/メモリの実測棒グラフ。

## 第3章：エネルギーゲートを“本番の単位”で較正する
- energy = T·logsumexp(logits/T)。OOD(BirdNET誤検出/対象外種)を録音平均energyで棄却。
- ⚠白状: 旧閾値は chunk 単位導出で、predict(録音平均)と**不整合**→真カモ32%誤棄却。録音単位で再導出。
- 動作点「真カモ最優先・保持≥0.90」: モデルを D-base-soup に替えたら energy が上方シフト→**旧2.717だと非カモFP0.88でゲート実質無効**→**3.081**へ再導出（モデル替えたら必ず再キャリブレ）。
- predict.py 潜在バグ2件を発見・修正: ①group別pipeline構造を読めずOODゲートが**常時無効**だった ②taxonomy stage2_modelを無視。
- 図: energy violin（真カモ vs 非カモ）, 閾値再導出で保持/FPがどう動くか。

## 第4章：カルガモ壁 — 世界最大級のモデルでも割れない
- 問題: カモ10種のうち**カルガモ↔マガモ**だけ混同が頑固。データを増やしても消えない。
- 決定的実験: Perch2.0の**ネイティブeBirdヘッド(14795クラス, 専用カルガモクラス)** を実カルガモ/マガモ各30録音に直接適用。
  - カルガモ録音: 専用クラス vs マガモ の2値**勝率0/30**、全クラスargmax=自種**0/30**（argmax先はマガモ12/ヒヨドリ12）。マガモ録音は30/30健全。
- 解釈: **世界最大級の学習をしたPerch本体でさえカルガモをマガモから引き剥がせない＝非対称崩壊（全てマガモに吸収）**。カルガモ壁は我々のデータ限界でなく**音響的に本質的**（交雑する近縁・声同一）。
- 図: Perchネイティブ混同（カルガモ→argmax先の分布 / マガモは自種）。

## 第5章：割れない壁を“設計”で受ける（複合クラス＝適応的解像度）
- 戦略転換: 音声でカルガモ種同定は死に筋。正解は **複合クラス「マガモ/カルガモ」(slash分類群)** で最頻種カルガモを捨てず誠実に出す（eBird慣行）。
- 適応的解像度: 種(既定)／割れないペアのみ複合／低信頼でカモ科sp.後退／非カモ棄却。再学習ゼロ（taxonomy の display_groups で表示置換）。
- 混同行列で「割れないペア」を実測してから複合化（カモは1個＝マガモ/カルガモのみ）。
- 図: 適応的解像度の決定木。

## まとめ（Part4）
- うまくいった: 2段化の群汎用配線、CPU運用化（蒸留の真価）、録音単位ゲート、複合クラスで誠実な出力。
- うまくいかなかった/受容: カルガモ壁は**消せない**＝精度でなく設計で受ける。OOD閾値はXC域の暫定でフィールド再較正必須。
- 教訓（格言）:
  > **「割れない」を認めることも設計。** モデルを叩いて0/30を1/30にするより、複合クラスで最頻種を救うほうが現場では正しい。
- 次Part予告: 「カモで型ができた。これを**カラス・カモメに横展開**して“分類器を量産する標準フロー”を作る。そして群によって**壁の有無**が違うことに気づく」。

# Part5「分類器を量産する — カラス、カモメ、そして標準フロー」🦆🐦‍⬛🕊

**一行テーマ**: 1群作る経験を“誰でも回せる標準フロー”に固める。横展開で見えた「群の性格（壁の有無）」の違い。

## はじめに（フック）
- カモで型はできた。だがユーザーの狙いは**他の群（カラス/カモメ）も載せる**こと。毎回ゼロから手作業は破綻する。
- 結論先出し: 種選択→モデル→ゲート→登録を**1本のドライバ＋生きた文書**に標準化。横展開して分かったのは「**群ごとに性格が違う**」＝カモは壁あり、カラスは壁無し。

## 第1章：標準作成フロー（生きた文書＋段階型ドライバ）
- `group_classifier_playbook.md`（判断則の本体・追記式）＋ `build_group.sh`（8段: data/prep/embed/train/eval/ood/confusion/register）。
- 思想: **判断点ではドライバは止まって情報を出すだけ**（自動化しない＝人間が判断則を守る）。config-<group>.yaml の差し替えだけで新群が回る。
- 図: 8段フロー図。

## 第2章：カラス(crow)を2群目に通す
- 4種(ハシブト/ハシボソ/ミヤマ/カササギ)、grade ラダー(A/AB/ABC) → **grade緩和は不要**（分離容易群＋データ非枯渇では clean-test 改善せず。カモの薄種=増やせと逆）。
- Lean vs KD: **差なし(録音f1 0.8815 vs 0.8833)→lean採用**（Part3「天井近いASTにKDは乗らない」の再確認）。
- 混同: Carrion最弱だが誤りが3クラスに散逸＝**割れる種ペア無し→複合不要(4種そのまま)**。カモのカルガモ壁と対照。
- OOD: 録音AUROC 在群vs同科Corvidae **0.906**、**同属Corvus(ワタリガラス等)でも崩壊せず=crow壁無し**。閾値2.610。
- ⚠白状エピソード: 夜間自動学習が `teacher_proba/val.npz` 取りこぼしで**KD枝全滅** → export `--splits train`固定が原因 → `train val`に根治。XC英名ミス(Common Raven→Northern Raven, Eurasian Jackdaw→Western Jackdaw＝IOC改名, 0件はgradeでなく名前)。
- 図: crow 混同行列（散逸）, 同属Corvus でも壁無しの energy 分布。

## 第3章：群の性格は「壁の有無」で決まる
- カモ=カルガモ壁あり(同科漏れ0.48を受容、複合化)。カラス=壁無し(同科漏れ0.115、複合不要)。
- OOD監査の読み方（2段前提の判断則）: stage1が科で前置フィルタ→実際に来るOODは**同科他種**＝**主指標は同科他種漏れ**。非同科FPは高くても実害小（来ない入力）だがstage1精度次第。
- 「壁が出た群ほど同科漏れは受容側へ倒す（閾値で殴れない）」。

## 第4章：横展開のために“配管”を直す（多群化の取り残し回収）
- 1群目(duck)は手作業の回避策で通っていた穴が、横展開で露呈:
  - `split.py` が共有 data/processed を**全種**で分割→config target で絞る修正（群フィルタ）。
  - OOD収集/監査(`download_ood`/`ood_fp_audit`/`build_group`)が **duck固定**→group別に多群化（master×group, in_family自動導出, Perch未整備ならAST単独監査）。
  - 教師proba export の `--splits train`固定（val欠落でKD全滅）を `train val` に根治。
- 教訓: **「2例目を通して初めて、1例目の“偶然動いてた”が露わになる」**。再現性＝執行可能性。
- 図（任意）: 修正前後で splits-gull が22種→6種に絞れる。

## 第5章：カモメ(gull)で3群目 — 大型白頭の壁を見にいく
- 6種(ウミネコ/ユリカモメ/セグロカモメ/オオセグロカモメ/カモメ/ズグロカモメ)。種選択＝北部九州で録れる種。
- XC英名の罠(再): **セグロカモメ=Vega Gull**（Herring Gull＝欧州別種を回避）。薄種は worldwide top-up。
- 仮説: **大型白頭3種(セグロ/オオセグロ/カモメ)は声が酷似＝カルガモ壁の再来か？** → 混同で実測（※本記事執筆時点の結果を記載）。
- 図: gull 混同行列（大型白頭が割れるか）, 種別 f1。
- ※ステータス: 学習中。結果が出てから本章を確定。

## まとめ（Part5）
- うまくいった: 標準フローで2群目(crow)を end-to-end 実証＝**再現可能を確定**。配管の取り残しを回収。3群目(gull)へ。
- 学び: **群には性格がある（壁の有無）**。同じフローでも、混同分析が出す“割れないペア”の数で複合化・ゲート設計が変わる。KDは相変わらず天井近い群では乗らない。
- 教訓（格言）:
  > **1個作るのと、量産できる形にするのは別の仕事。** 2例目で露わになった“偶然動いていた配管”を直して初めて、フローは標準になる。
- 次（予告）: gull 完走 → BirdProject本番配線（settings有効化）→ フィールド閾値再較正。エッジではなく**CPU運用ハブ(GT105)**へ。
